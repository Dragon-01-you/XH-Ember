# 术语对照表

左边是英文技能名/术语，右边是它在本项目里该怎么说、怎么理解。
**跟人说话时用右边，敲命令时用左边。**

## 流程类

| 英文 | 中文叫法 | 一句话说明 |
| --- | --- | --- |
| `/grilling` | 追问 | 一轮一轮问，把模糊的想法问成明确的选择 |
| `/grill-with-docs` | 带记录地追问 | 同上，顺手把定下来的词写进术语表、决定写进决策记录 |
| `/grill-me` | 追问（不留记录） | 同上，但什么都不保存。只在没有仓库的场合用 |
| `/wayfinder` | 探路 | 工程大到一个会话装不下、前方看不见路时，先画一张「决策地图」 |
| `/to-spec` | 出规格书 | 把已经谈定的东西综合成一份规格书，**不做新的访谈** |
| `/to-tickets` | 拆工单 | 把规格书切成一条条能独立做完的实现工单，并标好谁卡谁 |
| `/implement` | 实现 | 照着一张工单写代码，内部会调用红绿循环 |
| `/tdd` | 红绿循环 | 先写一个失败的测试，再写代码让它通过；一次一个切片 |
| `/code-review` | 双轴审查 | 两个并行子代理各查一个方向：合不合规范、是不是照规格做的 |
| `/pr` | 合并请求 | 写 PR 正文：摘要 + 证据 + 影响面 |
| `/retro` | 复盘 | 只改环境（规则、检查、工具），不改代码 |
| `/research` | 调研 | 派一个后台子代理去查一手资料，留下带引用的文件 |
| `/prototype` | 原型 | 写一段用完就扔的代码，只为回答一个具体问题 |
| `/triage` | 分诊 | 把**别人提的**议题过一遍状态机，决定谁来做 |
| `/diagnosing-bugs` | 排查缺陷 | 先做一个能复现的失败命令，再动手修 |

## 概念类

| 英文 | 中文叫法 | 一句话说明 |
| --- | --- | --- |
| `spec` | 规格书 | 一份写清楚"要做什么、不做什么、怎么算做完"的文件 |
| `issue` | 议题 | 追踪器上的一条记录。在本项目就是 GitHub 上的一张单子 |
| `ticket` | 票 / 工单 | 同上，但强调"一件待办的事"。本项目区分两种：**决策题**与**实现工单** |
| `ADR` | 决策记录 | 记一条"当时为什么这么定"的短文件，放在 `docs/adr/` |
| `map` | 决策地图 | 探路阶段的主议题，下面挂着一串决策题 |
| `frontier` | 当前可做的 | 没有被别的事卡住、现在就能动手的那几件 |
| `blocked by` | 被谁卡住 | 一条票要等哪些票做完才能开始 |
| `seam` | 测试接缝 | 在哪个公开边界上写测试。接口就是测试的落点 |
| `red / green` | 红 / 绿 | 测试先跑失败（红），再让代码通过（绿） |
| `scope` | 范围 | 这件事包含什么、不包含什么 |
| `out of scope` | 范围外 | 明确决定这次不做的，写清楚以免反复讨论 |

## 本项目特有

| 词 | 含义 |
| --- | --- |
| 浏览器桥 | 装在用户自己浏览器里的扩展 + 本地进程，借用户已登录的会话操作网页 |
| 券 | 云厂商发的优惠凭证。面额、余额、有效期可查 |
| 资质 | 与账号当下状态绑定的判定（学生认证还剩不剩、是不是新用户）。只能从页面看到 |
| 方案匹配 | 逐层提问猜出用户要什么，再给三个完整组合 + 一个明确推荐 |
| 关键节点 | 实名、绑卡、选套餐、付款、备案提交——必须机制层硬拦截 |
| 环境 | 用户能不能访问某个云厂商服务：能否直连、要不要代理 |
