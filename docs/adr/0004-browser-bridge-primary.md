# 主接入方式是用户自己浏览器里的扩展桥，不要求用户创建 API 密钥

我们通过一个装在**用户自己浏览器**里的扩展桥（用现成方案，比如 Kimi WebBridge、OpenCLI 一类，不自研），
在用户已登录的会话里操作云厂商控制台。不把"创建 AccessKey / 子账号 Token"作为主路径。

**原因**：让小白去控制台找 AccessKey、配子账号、加 RAM 策略，本身就是一道他过不去的坎。
把这道坎留给用户，等于把产品要解决的"不会"原样还给他。浏览器桥的优势是**零配置**：
账号已经登录着，插件在，就能动。

**代价**：控制台改版即失效，比官方 API 脆弱；且部分厂商（如 Netlify）的可接受使用政策用宽泛措辞
禁止"通过自动化方法访问网站"，改用扩展桥并不能消除这条解释风险，只能在选型时避开这类厂商，
或在方案里把它排除。

**配套**：官方 API 仍然保留，作为"愿意配置的用户可选加速"，不是主线。
